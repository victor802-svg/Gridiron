########################## BRIEF A — GRIDIRON_12 ##########################
# your calls on the record, and results that find you

Five phases, push each. All laws bind; MENTOR.md first; /closeout,
verdict slots empty.

THE OPERATOR'S RULINGS:
R1  The operator makes their own calls: pick a side + a tier (LEAN /
    SOLID / STRONG), graded on the same buckets and gates as the
    model. Optional per question — silence is not a call.
R2  The operator sees the model and the market before calling. So
    the operator is a THIRD FORECASTER CATEGORY — "you (informed)" —
    never merged with the blind record, labelled as informed
    everywhere it appears. Law 6 within the sport applies across
    forecasters as it already does for statistical vs LLM.
R3  Results-landed notifications go to BOTH the PC (Windows toast)
    and the phone (ntfy push).
R4  (mentor's, overrulable) Failure notifications — a MISSED slate,
    a task silent > 36h, a red gate — are a second channel, ON by
    default. The appliance sat stalled for days once with every
    screen green; that is exactly the moment a push exists for.

PHASE O1 — the call, as a record (commit "calls 1: schema + rules")
- operator_calls(id, created_utc, prediction_id, side, tier,
  claimed_prob, resolved_utc, outcome), append-only with the same
  triggers as predictions: no UPDATE, no DELETE, one resolution.
- TIER -> CLAIM: dated constants LEAN 0.55, SOLID 0.65, STRONG 0.75
  (bucket midpoints), stored on the row so a later change to the
  map never rewrites history. State in the docs that the operator's
  calibration is graded by tier bucket directly.
- BEFORE START ONLY: the server refuses a call once the game has
  started (structural — the same kickoff bound the MISSED rule
  uses). A call may be REVISED before start: a new row supersedes,
  the old row stays, and "latest before start" is the one graded.
  History shows the revision chain.
- Calls resolve in the same resolver pass as the prediction they
  attach to; a voided prediction voids its calls with the same
  reason.
- Authenticated operator only (already gated); no calls via any
  unauthenticated path; planted test.
- Law 5 check: tiers are confidence, not stakes. A planting that
  introduces any unit, amount, or bankroll field on a call fails by
  name.

PHASE O2 — entering a call (commit "calls 2: entry")
- On the desk's SELECTED PICK panel: a "Your call" block — two side
  buttons naming the sides in plain words (via side_named: "Alabama
  covers −30.5" / "ECU covers"), a LEAN / SOLID / STRONG segment,
  and one "Call it" button. After calling: the block shows the call
  with "revise" until start, then locks with "called before
  kickoff" and later the WIN/LOSS chip beside the model's.
- On the compact rows (phone): the same block inside the
  expansion.
- The tile / row shows a small mark when a call exists, and after
  resolution shows two verdict chips: model and yours.
- Nothing about the model's display changes for uncalled picks.

PHASE O3 — three forecasters on the record (commit "calls 3: record")
- The Record tab's tier table gains a forecaster selector with
  three options: statistical · LLM · you (informed). Each its own
  table, own gates, "unproven — N of 20" until earned. NEVER a
  combined view.
- One comparison line, gated at 20 settled calls: "On the N picks
  you called, you were right X%, the model Y%, the market Z%."
  Plain words, N stated, nothing shown below the gate.
- since-you-last-looked gains: "your calls: 3 right, 2 wrong" when
  any resolved.
- History rows carry the call and its outcome beside the model's.
- The plain-words scan runs over all of it; "informed" appears
  wherever the operator's numbers do.

PHASE O4 — results find you (commit "calls 4: notify")
- One notifier module with two channels and two message types.
  CHANNELS: Windows toast (PowerShell, no third-party module — the
  Windows.UI.Notifications COM path), and ntfy push (POST to
  https://ntfy.sh/<topic>; topic is a 32-char random string
  generated by tools/make_token.py into .env as GRIDIRON_NTFY_TOPIC;
  never logged; README explains the phone-side subscribe and that
  anyone holding the topic can read it — counts and team names
  only, never reasoning or the token).
- MESSAGE TYPES: RESULTS — sent by the resolve task only when it
  settled > 0: "MLB: 7 settled — model 4 right, you 2 of 3. CFB: 60
  settled — model 33 right." One message per run, all sports, never
  summed across sports into a total. FAILURES (R4, default on,
  GRIDIRON_NOTIFY_FAILURES=1) — a MISSED slate, a task silent >36h,
  a red verify gate: one line, the task name in words.
- Quiet hours honoured (default 23:00–07:00 local; results queue
  and send at 07:00 in one message).
- Notifications carry no market prices, no reasoning, no stakes;
  planting: a message containing a probability or a line fails.
- The schedule panel shows the last notification sent and its
  channel results, honest about a failed POST.

PHASE O5 — verification (commit "calls 5: qa")
1. Full suite, no skips; plantings named: a call after start; an
   UPDATE on operator_calls; a unit field on a call; a merged
   forecaster view; a notification containing a probability; a
   results message on a run that settled zero.
2. Renders: the rail with an open call block, a called tile, a
   resolved tile with two chips, the three-forecaster tier table
   (all unproven), desktop and 390px.
3. A real toast fired on the PC and a real ntfy push received (the
   operator installs the ntfy app and subscribes to the topic — if
   not yet done, mark "ntfy: ready, not received" honestly).
4. verify.py green; /closeout, verdict slots empty; push.

PHASE L1 — live data, fenced (commit "live 1: scores")
=====================================================================

- A LIVE POLL task: during any window where a game in a supported
  sport is scheduled to be in progress, poll the source's
  scoreboard every 90s (dated constant) and write score, period/
  inning/quarter, clock and status into the games table (games is
  data, not record — updating it is permitted; predictions are
  never touched). Outside windows the poll does not run at all —
  assert zero requests on a quiet day.
- The poller lives OUTSIDE the prediction import closure; the
  closure audit walks it and fails if live fields are reachable
  from any prediction module. Planting: import the live module
  from a sport's prediction path.
- Live status does NOT resolve anything. Only the resolve task,
  on a final, settles a prediction — assert that a game marked
  final by the poller alone leaves its predictions open until
  resolve runs. (The poller may TRIGGER resolve on final so results
  land within a minute of the game ending — that is a call to the
  existing idempotent resolver, not a second path.)
- Rate honesty: log requests per hour; the schedule panel shows
  the live poll's last run and request count.

PHASE L2 — the tile knows the game state (commit "live 2: tiles")
=====================================================================

Three tile states, one component:
- UPCOMING: as today.
- LIVE: a small pulsing mark in chrome (NOT green — green is wins
  and interactive), the score in mono ("ALA 21 · ECU 7"), and the
  clock/period in the corner ("3rd · 8:41" / "Top 6th"). The pick
  line and model number stay; the market/gap corner is replaced by
  the score. For totals show the running total against the line
  ("31 · under 58.5").
- FINAL: the WIN / LOSS / VOID chip replaces the tier edge's role
  for that tile; the final score stays in the corner.
- The frontend polls a compact /api/live endpoint every 60s ONLY
  while the current slate has any live game; stops when none.
  A tile changing state re-renders in place — the grid does not
  re-sort while a slate is in progress (sorting live games by
  confidence would shuffle the screen under the reader).
- The rail's selected pick mirrors the three states, adding the
  score line under the pick sentence when live/final.
- since-you-last-looked counts results as they land.

PHASE L3 — motion with a vocabulary (commit "live 3: motion")
=====================================================================

ONE vocabulary, in one CSS block, and a guard:
- Durations: 150ms for state changes (chip appearing, tile
  selection, filter changes), 200ms for panel content swaps in the
  rail. Nothing longer. Easing: one curve (ease-out).
- Properties allowed to animate: opacity, transform (translate/
  scale within 2%), background-color, border-color. Nothing else —
  no height/width animation, no box-shadow glow, no color cycling.
- The FINAL flip: the chip fades in over 150ms and the tile's
  ground settles to the resolved shade; no bounce, no confetti, no
  sound. A loss looks like a loss quietly.
- Skeleton placeholders during first load (tiles as hairline
  shapes), gone within one frame of data.
- prefers-reduced-motion: every transition 0ms, states still
  change instantly, the live pulse becomes a static mark.
- GUARD: a stylesheet scan that fails on any transition/animation
  outside the vocabulary — duration > 200ms, a disallowed
  property, a second easing curve, or any keyframe other than the
  live pulse. Planting: a 400ms bounce on a chip.

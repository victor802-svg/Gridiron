## Ruling 2 — and a restart setting that had never restarted anything

**The task now runs the interpreter**, not the bundle:

```
ACTION: ...\.venv\Scripts\pythonw.exe -m gridiron.cli serve
StartWhenAvailable=True  MultipleInstances=IgnoreNew  ExecutionTimeLimit=PT0S
triggers: AtLogOn + every PT2M
```

### Two things had to be fixed to get there, and neither was expected

**`pythonw.exe` has no console, so `sys.stdout` is None.** `print()` copes and
returns; `logging.StreamHandler(sys.stdout)` does not, and uvicorn builds one
at startup. The first registration failed instantly with exit 1. `cli.main`
now binds both streams to the null device when they are absent, before
anything imports uvicorn and captures what it finds. Using `python.exe`
instead would have traded a startup failure for the exit this installer's own
comment warns about: a console process dies `0xC000013A` when its window
closes, and the interface is the one process that must outlive that.

**`RestartCount 3 / RestartInterval 1 minute` restarts nothing.** That setting
has been on this task since 2026-09-07 and had never been tested. Measured:

```
killed the serving process   22:15:14
90 seconds later             state=Ready  lastResult=0xFFFFFFFF  nextRun=<empty>
```

`nextRun` empty is the whole answer — nothing was queued. Windows applies
"restart if the task fails" to a task that failed to START, not to a
long-running action whose process was killed. So the mechanism is the one
`Gridiron-Live` already uses: **a repeating trigger every two minutes with
`MultipleInstances IgnoreNew`**. Up, the attempt is ignored and costs nothing;
dead, it comes back. `RestartCount` is kept for the case it does cover.

### The proof the ruling asked for

| | kill | back | elapsed | `/api/health` |
|---|---|---|---|---|
| first, before the repeating trigger | 22:15:14 | 22:18:02 | 159 s | `81becd4106b5` |
| second, with it live | 22:18:20 | 22:20:03 | **99 s** | `81becd4106b5` |
| third, releasing this commit | 23:06:56 | 23:08:04 | **63 s** | `0a86f2e6302c` |

The second and third are the real figures: under two minutes, unattended, and
the commit hash comes back with them. The first spans the period when nothing
was queued at all, and is kept because it is the measurement that found the
fault.

**The third is also the new release path's first use.** Gate, commit, push,
then kill the interface and let the task bring it back on the new code:
`/api/health` answered `0a86f2e6302c` and `git rev-parse HEAD` is
`0a86f2e6302c`. That pair is the build identity now, and it is checkable by
anyone in one line without a hash to look up.

### The bundle, retired rather than erased

`desktop/gridiron.spec` and `desktop/make_shortcut.ps1` are kept and marked —
a step that vanishes is a step nobody can audit — and neither tells anyone to
build any more. `CLAUDE.md` gains **the release path**, which had never been in
a file at all: it was a sentence the operator repeated, and a step that lives
only in a habit cannot be edited when it changes. It is now **gate, commit,
push, confirm**, and the build identity is the commit hash plus what
`/api/health` answers — which says what is SERVING rather than what was BUILT.

The slate renders shortlisted questions only. Football's cap is thirty; 107

### Two defects found looking for those cards, both fixed

**The filter row was counting what it does not filter.** Measured on the live
NFL slate before the fix:

| tab | said | cards it left on screen |
|---|---|---|
| All | 107 | 30 |
| Point spread | 29 | 4 |
| Moneyline | 16 | 4 |
| Passing yards | 20 | 4 |
| Receiving yards | 15 | 3 |
| Rushing yards | 11 | 4 |
| Receptions | 8 | 4 |
| Passing touchdowns | 8 | 4 |

Every tab overstated by three to seven times. This is the operator's ruling of
2026-09-08 on this very row, from the other end: then the filter did not reach
everything it counted; now the count did not describe what the filter reaches.
`_market_tabs` counts the shortlisted cards — the ones the tab can leave on
screen. **Which questions reach the slate is untouched.**

**And three cards were counted under a tab that could not show them.** With
the counts corrected one tab still disagreed: Passing yards said 7 and produced
4. Predictions 6, 32 and 39 are early rows whose `prop_type` column is NULL, so
the tab row derived `passing_yards` from the source card while the card itself
carried `recommend`'s bare `prop`. They were reachable from no tab but All.
There is one derivation now, `views._market_key`, and both ends read it.

Both are tested, and the test was **proved on the unfixed code** — planted the
old count, watched it fail (`the 'All' tab says 22 and leaves 20 cards on
screen`), restored. The test builds twenty-two questions against a cap of
twenty on purpose: with every question shortlisted the old count and the new
one agree and the defect hides, which is how it survived.

### A third one, measured and NOT fixed

With a tab chosen, the group heading still reads **"Watching — 30 more"** over

the browser — and the heading is composed server-side over the unfiltered

The fix is to send the headings per market and have the renderer place one;
that is a payload-shape change, this session already has two of those in it,
and payload-shape changes have twice this week taken more than they were aimed
at. In FOLLOWUPS with the sketch.

## A flake I nearly blamed on myself

The gate came back with two browser failures, both
`ElementHandle.click: Element is not attached to the DOM`. Reverting
`views.py` to HEAD made one of them pass, which looked like an answer and was
one sample each way.

**Measured properly: one failure in three runs with the change in place.** A
flake, not a regression — and blaming the last thing that touched the file is
exactly how a flake gets a wrong owner and a real fix gets reverted.

**The tests were wrong.** `page.query_selector(...)` returns a SNAPSHOT of one
node; `renderWeek` rebuilds `#today` with `host.innerHTML = ''`, so any render
landing between the query and the click leaves the handle pointing at a node
that has left the document. Both now use a locator, which re-resolves at click
time and retries while the node is detached. Eight runs, eight passes; nothing
either test asserts has changed.

## The release path was wrong for about a minute

Pushing the close-out commit, `/api/health` reported `508b41697977`
**immediately** — from a process that had been up since 23:08 running
`0a86f2e`. No restart, no reload, and the number changed anyway.

**The health line was reading the checkout, not the process.** Under the
bundle it could not: a frozen build carries a stamped commit and the stamp
cannot move under it. From source there is no stamp, so `buildinfo.build_id`
fell through to `repository_head()` — read fresh on every request. A
`git checkout` would have "changed the running version" without a byte of code
being reloaded, and Python does not hot-reload.

On any other day that is a cosmetic wrinkle. On the day `/api/health` became
half the build identity it is the identity being wrong, and it would have been
wrong in the flattering direction: a release that was never restarted would
report itself live.

**`api.serve` pins the answer before it binds the port** (`buildinfo.freeze`).
The health line now describes this process; `repository_head()` still tells the
colophon how far that process has fallen behind, which is what this module was
written for. Tested with the checkout moved underneath it.

**And the release path in CLAUDE.md gained the step it was missing:** gate,
commit, push, **restart**, confirm. The restart is what makes the confirm mean
anything — and if it is skipped, the health line now says so.
